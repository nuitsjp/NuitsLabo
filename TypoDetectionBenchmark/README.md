## 中断時点の所感（2026-10-08）

**測定上はGPT-6 Lunaの差分補正lowが有力ですが、実運用で確実に補正できると結論づける段階ではありません。** 特に、同じ文字列が文脈によって正しい箇所と誤字の箇所に分かれる場合、修正対象を特定できる差分をAIが返せるかが重要です。以下の推奨は今回の評価範囲での暫定的なものとして扱い、ここで作業を中断します。

| 方式 | AIが返す内容 | 利点 | 注意点 |
|---|---|---|---|
| 全文補正 | 修正後の文章全体。修正不要でも全文を返す。 | アプリが置換箇所を特定する処理は不要。 | 長文ほど出力が増える。見逃しや、正常な表現・空白などの不要な変更は起こり得る。 |
| 差分補正 | `[["置換前", "置換後"], ...]`。修正不要なら `[]`。 | 少数の修正なら出力が短く、指定範囲以外はコードで原文を保持できる。 | 置換先の内容だけでなく、対象を一意に特定できる置換元も正しく生成する必要がある。 |

例えば「工場の機械を点検し、学ぶ機械を増やす。」では、最初の「機械」は正しく、後ろだけを「機会」に直す必要があります。`[["機械", "機会"]]` だけではどちらを指すか復元できず、全置換すると正しい箇所まで壊します。今回の指示では、`[["学ぶ機械", "学ぶ機会"]]` のように前後の文脈を含め、置換元が原文に一度だけ現れるよう求めています。

**文脈を含めれば表現できることと、AIが毎回その指定を正しく返せることは別です。** 現在のコードは、置換元が存在しない場合、複数箇所に一致する場合、修正範囲が重なる場合に適用を拒否します。これは誤った置換を防ぐ検証であり、補正成功の保証ではありません。拒否した場合は補正未完了となり、全文補正への自動切り替えは実装していません。また、適用可能な差分でも見逃し・誤修正は残り得ます。必要な文脈が長くなれば、差分の出力削減効果も小さくなります。返答形式は[プロンプト](Prompts.cs)、適用条件は[補正処理](Evaluation.cs)に記載しています。

今回の追加評価はAPI・出力形式エラー0件で、GPT-6 Luna差分lowは384観測中383観測が期待値と完全一致しました。残る1件は期待値「公開」に対する自然な別修正「展示」です。ただし、この結果を同一文字列の正誤混在に対する十分な検証とみなすことはできません。再開時には、正誤混在、同じ誤字の複数出現、繰り返しの多い文章を含む専用ケースで、対象箇所を正しく選べるかと、適用拒否がどの程度発生するかを確認する必要があります。

800文字ではGPT-6 Lunaの全文補正が平均約4.95秒・1,000入力あたり約$0.510、差分補正が約1.65秒・約$0.178でした。ただし、全文は推論量medium、差分はlowであり、差のすべてを出力形式の効果とは解釈できません。両方式とも入力の全文を読みます。全文方式も正確性を保証するものではなく、差分の適用可能性と文章としての修正精度を分けて比較する必要があります。

JevやDecisionsによる事前判定は、全文・差分のどちらにも必須ではありません。判定が誤字を見逃すと補正を呼ばないため、後段では回復できません。今回のJev既存設定はその見逃しが多く、見逃しを避ける用途には推奨しません。旧OpenAI Decisionsは今回見逃しがなく速度面では有利でしたが、400・800文字では直接差分補正より高コストでした。実際の誤字率で費用の優劣は変わるため、「長文では判定APIを使わない」と一般化せず、現時点では直接補正を基本候補として考えます。

## 誤字がある場合だけ直すための推奨構成

**今回の追加評価では、GPT-6 Lunaの差分補正（推論量low）を中心に選ぶのを推奨します。** 正常文192観測をすべて維持し、誤字文は191/192が事前の期待値と完全一致しました。残る1件も「航海」を「展示」に修正しており、期待値の「公開」とは異なる自然な別修正です。

| 優先すること | 推奨構成 | 今回の結果から選ぶ理由 |
|---|---|---|
| 100・200文字の速度と費用、または各文字数での応答時間 | **旧OpenAI判定＋GPT-6 Luna差分補正low** | 誤字の見逃しは0/192。直接補正と同じ正解数で、各文字数の推定平均時間が短い。100・200文字では費用も下がる。 |

## 実行

.NET 10 SDKを使います。API呼び出しには `OPENAI_API_KEY`、TypeSafeを選ぶ場合には `TYPESAFE_API_KEY` をプロセスまたはユーザー環境変数に設定してください。秘密値はログに保存しません。

```powershell
cd D:\nuitsjp\NuitsLabo\TypoDetectionBenchmark

# APIを呼ばない78項目の自己テストとコーパス検証
dotnet run -c Release -- self-test

# 従来の約120文字評価の設定を再測定する
dotnet run -c Release -- run --variants decision-openai-english,correction-luna56-v3-edits-low --split holdout --repetitions 2

# 保存済みの結果をAPIなしで再集計する
dotnet run -c Release -- summarize results/holdout-20261008
```

`--corpus path.json`、`--split development|holdout|all`、`--variants`、`--repetitions`、`--seed`、`--output` で測定条件を指定できます。引数なしではヘルプを表示し、`list` で全候補を一覧にします。`run` の `--variants` を省略した場合は、従来の既定値であるOpenAI英語判定とGPT-5.6 Luna差分lowだけを実行します。今回の8設定を再現する手順は[文字数別レポート](LENGTH_SCALING_BENCHMARK.md#5-再現手順)を参照してください。外部の文字数別コーパスを使う場合は `--corpus` と `--split all` を指定します。`--limit` は先頭の少数件による接続確認用で、正常文だけになる場合があるため精度比較には使いません。

各実行は逐次・順序シャッフルで測り、固定待機や自動再試行は行いません。エラーを含めて1件ずつ保存し、不正解を分母から除きません。エラーを含む実行は終了コード1、全要求が正常完了した実行は0です。使用量が不明なら費用も不明として扱います。今回の費用はAPI使用量から算出した標準USDの推定額であり、請求額そのものではありません。

従来の評価では実APIを合計924回呼び出し、標準単価での推定総費用は$0.091470006でした。候補実験の4件の無効な差分は失敗として記録しています。独立評価384回はAPI・出力形式エラー0件でした。追加評価では3,072要求・エラー0件を確認しました。外部コーパス読み込みの17項目を加えた78項目の自己テストと、新規192文の文字数・誤字位置・修正結果を検証しています。
