独立検算では、3,072件の欠落・重複、全応答と保存採点、使用量からの料金計算、文字数別32群、分類別608群、構成別80群・7,680観測に不整合がないことを確認しました。入力キャッシュはOpenAI補正の114要求・146,716トークンで確認され、費用へ反映しています。TypeSafeのキャッシュ情報は未提供です。反復や同じ題材を含む本評価のキャッシュ条件は、実運用と同じとは限りません。

新しく作成した24の題材を、4つの文字数帯へ展開しました。同じ題材を識別する番号を `FamilyId` と呼びます。家事、スポーツ、地域活動、科学、学校、業務などを扱い、各文章に正常文と対応する誤字文を用意しています。

| 目標文字数 | 正常文 | 誤字文 | 正常・誤字を合わせた実測文字数 |
|---|---:|---:|---:|

正常文は目標文字数の±5%を許容し、自然な説明を増やして長さを調整しました。誤字文は正常文へ誤りを入れて作るため、脱字や重複の分だけ長さが変わります。句読点、英数字、空白も文字数に含めます。文字数とAPIのトークン数は別の値として記録します。

位置は、誤字を含む置換元の開始位置を本文長で割って確認しました。単一誤字の目安は冒頭0〜0.30、中央0.35〜0.65、末尾0.70〜1.00です。正常文には固有名詞、英数字、空白、正当な表記ゆれも含め、不要な変更を検出します。

実行前に、文字数、置換元の一意性、置換範囲の非重複、全置換を適用すると正常文へ完全に戻ることを検証しました。文章の不自然な助詞や手順の前後関係もレビューし、測定前に修正しています。

## 2. 正解の決め方

判定APIでは、正常文を「誤字なし」、誤字文を「誤字あり」と判定した場合を正解とします。正常文の誤検知と誤字文の見逃しを分けて集計します。

補正APIでは、正常文は原文を一文字も変えないこと、誤字文は事前に定義した期待修正文のいずれかと全文が一致することを正解とします。空白・句読点も比較し、前後の空白を取り除いたり、表記をそろえたりしてから採点する処理は行いません。複数誤字の文は、すべての誤りを修正し、ほかの箇所を変えない場合に正解となります。

実行前のレビューで自然な別解を確認した次の2題材だけは、誤字文の期待値を2通り登録しました。4つの長さすべてに同じ扱いを適用しています。

| 題材番号 | 誤字文の修正で認める表現 |
|---|---|
| Family 10 | 「迷惑にならない」「迷惑とならない」 |
| Family 23 | 「糸を針に通します」「糸を針へ通します」 |

正常文は、この別解へ言い換えた場合も不正解です。元から正しい文章を維持する能力と、誤った文章を直す能力を区別するためです。

期待値との不一致は、必ずしも意味の修復に失敗したことを示しません。自然な別表現への修正と、誤字の放置や過剰修正は、出力差分を確認して区別します。結果を見てから期待値を追加して点数を上げることはしません。

HTTP失敗、拒否、打ち切り、不正なJSON、適用できない差分はエラーとして記録します。正解率の分母にはエラーも含め、失敗を「正常文だった」と扱う処理や、失敗した要求だけを除く処理は行いません。

## 4. 応答時間と費用の読み方

応答時間は、要求の送信開始から応答本文を最後まで読み取るまでです。API応答と出力形式の検証に成功した要求について、平均、中央値、P95を集計します。P95は時間を小さい順に並べ、件数の95%に当たる順位を切り上げて求めます。最初の要求も含み、最初の接続に伴う影響を確認できるよう、API種別ごとの初回要求には印を付けています。

正解率はエラー込み、応答時間は成功応答のみという分母の違いがあります。速度を比較するときはエラー数も合わせて確認します。1設定・1文字数帯の予定観測数は96回であり、P95だけから本番環境の遅い応答や最大時間を保証することはできません。

費用はAPIから返された使用量と、2026-10-08に確認した標準単価を使うUSDの推定額です。実際の請求額ではなく、無料枠や為替換算は適用しません。補正APIのキャッシュ入力は返された使用量に従い、推論トークンは出力トークンの内数として扱って二重加算しません。計算に必要な使用量が不明な場合は費用も不明とし、ゼロとは扱いません。単価と出典は [ApiClient.cs](ApiClient.cs) と実行時のmanifestに記録しています。

判定と補正を組み合わせる場合は、同じ入力ID・同じ反復番号の保存応答を突き合わせ、「誤字あり」と判定したときだけ補正を利用したものとして再計算します。時間と費用は必要になった呼び出しだけを合算します。これは保存応答を使った推定であり、判定から補正までを連続実行した実測ではありません。元の文章の誤字率は50%で、実運用の誤字率や誤検知・見逃しによって補正回数と費用は変わります。

## 5. 再現手順

.NET 10 SDKを使用します。構成全体の再集計にはPython 3も使用します（標準ライブラリのみ）。全8設定を実行するには、`OPENAI_API_KEY` と `TYPESAFE_API_KEY` をプロセスまたはユーザー環境変数へ設定します。

以下は今回と同じコーパス・8設定・反復数・乱数の種で再測定するコマンドです。出力先には日時を付けた新しいディレクトリを指定します。

```powershell
cd D:\nuitsjp\NuitsLabo\TypoDetectionBenchmark

# ネットワークを使わない自己テスト
dotnet run -c Release -- self-test

$lengthVariants = @(
    'decision-openai-baseline'
    'decision-openai-english'
    'decision-typesafe-baseline'
    'decision-typesafe-lean-calibrated'
    'correction-luna6-v3'
    'correction-luna6-v3-edits-low'
    'correction-luna56-v3'
    'correction-luna56-v3-edits-low'
) -join ','
$lengthRunDirectory = 'results/length-holdout-rerun-' + (Get-Date -Format 'yyyyMMdd-HHmmss-fff')

dotnet run -c Release -- run --corpus corpora/length-holdout-20261008.json --split all --variants $lengthVariants --repetitions 2 --seed 20261008 --output $lengthRunDirectory

# 完了後、保存した応答をAPIなしで再集計する
dotnet run -c Release -- summarize $lengthRunDirectory
python -X utf8 scripts/analyze_length_benchmark.py $lengthRunDirectory
```

コーパスの区分名は `length-holdout` です。コマンドでは `--split all` を指定して全192文を読み込みます。`--variants` を省略すると8設定すべての比較にはならず、`--limit` を使うと予定した文数を満たしません。出力先のディレクトリが既に存在する場合、実行は拒否されます。

`manifest.json` は実行条件と正解、`requests.jsonl` は全要求の応答と使用量、`summary.json` と `summary.md` は文字数帯・設定別の集計です。すべての予定要求を処理した場合は、件数とエラー数を記した `completion.json` も保存します。モデルの出力やサービス負荷は変動するため、同じ乱数の種でも測定値が完全に一致することを意味しません。

## 6. この評価の制約

192文は24題材から作った合成文です。同じ題材の長さ違い、正常文と誤字文、2回の反復は互いに関連します。3,072要求を3,072個の独立した入力として扱うことはできません。

長い文章には同じ題材の説明を追加しているため、文字数とともに内容や表現の種類も増えます。同じ題材では誤字数を固定しているので、長くなるほど文字数あたりの誤字数も減ります。結果の違いを文字数だけの影響とは断定しません。単一誤字の「種類×位置」ごとの題材は1つであり、その集計だけで誤字種や位置に対する一般的な性能を断定するには不十分です。

正常文維持と期待値一致は厳密に測れますが、すべての自然な修正表現を列挙した評価ではありません。自然な別解やコーパス上の問題が見つかった場合は、事前に固定した点数を維持し、意味上の修復状況を注記します。実データの文体や固有名詞、曖昧な用語、誤字率が異なる環境への精度保証には使いません。
